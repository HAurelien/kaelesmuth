# Schema

What every kind of note holds, and how time and place are written. [[Vault conventions]] says why the vault is laid out this way; this note is the precise version that tools rely on.

The rules live in `_tools/schema.json`. `_tools/check_vault.py` checks the whole vault against them and runs before every commit. The tables at the bottom of this note are generated from the schema file, so change the schema file, not the tables.

## Time

Every year is a whole number in a named calendar. Years before 0 (PME) are negative: 1 PME is `-1`.

| Case | How to write it |
|---|---|
| Known year | `year: 2758`, `calendar: aethernam` |
| Known day or hour | add `date: "2758-01-01"` or `date: "2758-01-01 01:00"`. The date's year must equal `year`. Month only is fine: `date: "2740-10"`. |
| Several years | `year: 2740`, `end_year: 2745` (plus `end_date` if known). Leave `end_year` empty for an event within one year. |
| Approximate | write your best guess as the year and add `approximate: true`. |
| Unknown | leave `year` empty. If you know it came before or after another event, say so with `after: ["[[Other event]]"]` or `before: [...]`, so it can still be ordered. |
| Before 0 | `year: -120` (120 PME). |

`calendar` is required as soon as a note has any year. Each planet has its own calendar (`aethernam`, `zephyrion`), and a note uses one calendar for all of its years. An event on Zephyrion is dated in the Zephyrion calendar. An event on both planets is dated in whichever calendar it was recorded in; once the conversion exists (see [[Backlog]]), tools will show it in both.

The same applies to everything else that exists for a while. Each kind of note has a start and an end property: characters `born`/`died`, organizations `founded`/`dissolved`, places `from`/`until`, events `year`/`end_year`. Empty start means "has always existed as far as we know", empty end means "still exists or unknown". This is what tools use to answer "what does the world look like in year X".

## Place

| Case | How to write it |
|---|---|
| Known place | `location: ["[[Place]]"]`, the most precise place you know. The place's own `parent` says what it's inside of, so there is no need to list the city and the country. |
| Several places | list them all: `location: ["[[A]]", "[[B]]"]`. |
| Only the planet is known | `location: ["[[Aethernam]]"]`. |
| Unknown | leave `location` empty and fill `planet` if you know it. |
| On both planets | `planet: ["[[Aethernam]]", "[[Zephyrion]]"]`. |
| Off-planet (the Ether) | `location: ["[[Ether]]"]`, `planet` empty. |

`planet` on an event is the planet(s) it happened on. The checker warns when a location is on a planet the event doesn't list.

So an event can have a place, a time, both, or neither, and each of those is written one way only.

## Links

Properties that point to other notes hold quoted links, and the checker makes sure each one exists and is the right kind of note (a `location` is a place, `participants` are characters, gods, organizations or species). Links in the text that lead nowhere are reported as warnings, since Obsidian allows them for notes you haven't written yet.

## What the checker reports

**Errors** block the commit: a broken link in a property, a value of the wrong kind (`year: "about 2700"`), a date that contradicts its year, an end before its start, a year without a calendar, a note in the wrong folder, two notes answering to the same name, a property the conventions forbid (`children`, `members`, `subsidiaries`...).

**Warnings** don't block: they look wrong but might be what you meant. A character in an event before their birth or after their death, a link to an unexpected kind of note, a property that isn't in the schema yet, a partner who doesn't list the other back.

Characters and events are only compared when they use the same calendar, until the conversion exists.

## Running it

From the vault folder:

- `python3 _tools/check_vault.py` lists errors and warnings.
- `python3 _tools/check_vault.py --json` gives the same report for other tools.
- `python3 _tools/check_vault.py --write-docs` regenerates the tables below after a change to `schema.json`.

The commit hook is in `_tools/hooks`. It is switched on once per copy of the vault with `git config core.hooksPath _tools/hooks`. To commit despite errors, use `git commit --no-verify`.

## Adding a property

Add it to `_tools/schema.json` under its type (with `type`, and `to` for links), then to the template in `_templates`, then run `--write-docs`. Properties not in the schema still work in Obsidian; the checker only warns about them.
